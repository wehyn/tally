# Tally Home Screen PWA Design

- **Status:** Draft for owner review
- **Date:** 2026-10-11
- **Scope:** Install Tally as a full-screen Home Screen web app on iPhone and keep Tally's own routes inside that app window.

## Problem

Tally's mobile navigation works, but after adding the site to the iPhone Home Screen with **Open as Web App** enabled, navigating to sections other than Home can show Safari controls in the same window. The desired experience is a full-screen app window across Tally's sections.

The current application has a mobile bottom navigation built from same-origin Next.js links. Its root route redirects to `/dashboard`. The root layout sets a theme color and `viewportFit: "cover"`, but the project has no web app manifest, Apple web app metadata, or service worker.

Apple documents standalone display as the mode without browser-provided toolbars. Web apps also have a navigation scope; links outside that scope may open in Safari. Tally's section links appear to remain on the same origin, so the exact trigger for the reported controls is not yet established. The implementation must verify the behavior on a real iPhone rather than treat the missing manifest as a proven root cause.

## Goals

- Launch Tally from its Home Screen icon without Safari's address bar, back button, share, refresh, settings, or Safari controls.
- Keep every Tally route, including `/dashboard`, `/transactions`, `/accounts`, `/bills`, `/debts`, `/goals`, `/settings`, `/admin`, and `/login`, within the installed app's declared scope.
- Preserve the existing app shell and mobile bottom navigation.
- Require an internet connection. Do not promise offline reads or writes.

## Non-goals

- Offline caching, queued writes, synchronization, or conflict resolution.
- Push notifications, badges, background work, or a native iOS wrapper.
- Adding an in-app back button or changing the existing mobile navigation.
- Changing authentication, server routes, financial data storage, or API behavior.

## Design

Add the minimum standards-based PWA configuration needed to declare Tally's identity, launch behavior, and route scope:

- A web app manifest with `name` and `short_name` set to Tally, `start_url: "/"`, `scope: "/"`, `display: "standalone"`, the existing theme color (`#f5f6f2`), a matching background color, and 192×192 and 512×512 PNG icons derived from Tally's existing brand mark.
- Next.js metadata that links the manifest and declares the iOS Home Screen app title and standalone capability. Provide a 180×180 PNG Apple touch icon derived from the same brand mark.
- Keep the existing `viewportFit: "cover"` setting and use the existing app shell and navigation unchanged.
- Do not add a service worker. Tally will continue to require network access for pages and actions, and no finance data will be cached or queued for later submission.

The `/` launch route redirects to `/dashboard`; the private layout already redirects signed-out visitors to `/login`. Both destinations remain inside the root scope. Existing mobile navigation links are same-origin paths and should therefore remain in the standalone window. Links that intentionally leave Tally's origin are outside this guarantee and may open in Safari.

The implementation must use the manifest and metadata conventions documented for the installed Next.js version. The repository's `AGENTS.md` requires reading the matching guide from `node_modules/next/dist/docs/` before writing code.

## Behavior and failure handling

- If the app is opened through its Home Screen icon, it uses standalone display. Opening the same URL in Safari continues to use normal Safari UI.
- If a manifest or icon cannot be loaded, the site remains usable as a regular website; installation appearance may fall back to iOS defaults.
- Existing authentication redirects and session behavior remain unchanged.
- No offline fallback is introduced. Network-dependent navigation and actions retain their existing failure behavior when disconnected.
- If an in-scope Tally section still opens Safari UI after the explicit scope is deployed, inspect the actual URL, redirects, scheme, host, and port on the device before making another code change. The current repository links do not explain an origin change.

## Acceptance criteria

1. The generated manifest is served successfully and declares `/` as both launch path and scope, `standalone` display, app names, theme/background colors, and 192×192 and 512×512 PNG icon assets. The rendered document references a 180×180 PNG Apple touch icon.
2. The rendered document includes the manifest reference and iOS standalone metadata, while retaining the existing viewport configuration.
3. From a newly installed Home Screen icon on a real iPhone, `/` reaches the dashboard when signed in and the login page when signed out, without Safari controls.
4. Tapping every visible mobile navigation item keeps its Tally destination in the same full-screen app window without Safari controls.
5. The ordinary Safari visit remains usable and retains browser controls.
6. No offline capability is claimed or added; there is no service worker, offline cache, or deferred write queue.

## Verification

- Inspect the built HTML and manifest response for the declared metadata, scope, start path, and icons.
- Exercise the root and authenticated redirects plus each mobile navigation destination with the existing browser tooling.
- Perform the acceptance check on a real iPhone after deploying the metadata. If the Home Screen entry does not pick up the new configuration, remove and add the icon again before concluding the behavior is unchanged.
- Record the iOS version and the final URL (including scheme, host, and port) when reporting device results, so a scope or redirect mismatch can be distinguished from an iOS display issue.
