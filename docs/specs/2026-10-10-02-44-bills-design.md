# Bills tab design

## Goal

Add a Bills tab for recurring payments and subscriptions. It shows each bill's expected amount, schedule, next due date, and upcoming occurrence. When an occurrence is due, Tally automatically records it as an expense, even if payment has not been confirmed.

## User-facing behavior

- A bill has a name, expected amount, weekly/monthly/yearly schedule, next due date, financial account, and expense category.
- The Bills page lists active bills by next due date and provides create, edit, and archive actions. Archived bills remain available in an archived list. Bills appears in desktop and mobile navigation.
- The page explains that each due occurrence is recorded as an expense whether or not payment has been confirmed.
- A single daily job runs at 02:00 Asia/Manila and once on app startup. For every occurrence due on or before today, it creates an expense dated with that occurrence's scheduled date, then advances the bill to its next scheduled occurrence. If Tally was offline, all missed occurrences are caught up.
- Generated expenses use the bill's saved amount, account, and category. A user can edit a generated transaction in the ledger if the actual charge differs; the edit does not change the bill defaults or its schedule.
- Archiving stops future postings. Transactions already created remain in the ledger and continue to affect balances and spending totals.
- Monthly and yearly schedules stay anchored to their original calendar day. A date that does not exist in a shorter month/year is clamped to that period's last day and returns to the anchor date when possible. Weekly schedules advance by seven days. Changing a bill's cadence or next due date establishes a new anchor for future occurrences.
- The initial due date is the next occurrence, not a historical start date; creating or editing a bill does not synthesize occurrences before its active schedule. A due date may be today or later.

## Data and execution

- Add a user-owned SQLite `bills` table with amount in PHP minor units, frequency, next due date, calendar anchor, account/category references, archive state, and timestamps. Existing users and ledger rows require no data migration beyond the additive schema.
- Add authenticated, same-origin bill APIs following the existing route patterns and Zod request validation. Enforce owner checks for bills, accounts, and expense categories at every write boundary.
- Add bill methods to the existing SQLite store. The scheduled processor re-reads each bill's current next due date while holding an immediate database transaction, then writes one expense and advances one occurrence in that same transaction. A retry or restart therefore sees either both changes or neither, preventing duplicate occurrences.
- A generated expense is an ordinary expense transaction named for the bill, dated on the scheduled occurrence, and linked to the saved account/category. Existing transaction edit and delete flows continue to apply; changing a transaction does not change the recurring bill.
- Run one processor with the long-lived Tally app and its existing SQLite database. The deployment already requires one app instance for this database. Protect the job against overlapping runs with SQLite's immediate transaction and current due-date state.

## Boundaries

- No manual “Mark paid” step, bank connection, automatic withdrawal, email/push notification, custom intervals, or payment-status tracking.
- A posted expense represents the scheduled bill and can reduce balances before money actually leaves the account. This is intentional and user-approved.
- Frequencies are weekly, monthly, and yearly only.

## Acceptance checks

- Bills are private to their owner; accounts and expense categories must belong to that owner.
- Creating, editing, and archiving bills preserves existing transaction behavior and ledger history.
- One due occurrence creates exactly one expense and advances the schedule atomically. Restarting or overlapping the processor does not duplicate it.
- Missed occurrences are posted once each with their original scheduled dates. Archived bills are never posted.
- Weekly, monthly, yearly, month-end, and leap-day date calculations retain their anchors.
- A generated transaction can be edited without changing future bill amounts or dates.
- Bills is reachable in desktop and mobile navigation.

## Verification plan

Add focused store and date tests for schedule arithmetic, catch-up, archival, and retry/concurrency behavior; route coverage for owner isolation and input validation; and a browser check of the Bills flow at desktop and mobile widths. Run the repository's typecheck, lint, test, and production build commands after implementation.
