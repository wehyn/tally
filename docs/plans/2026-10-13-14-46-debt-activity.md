# Debt Advances and Person Activity Implementation Plan

> Historical plan. Its incoming-repayment-as-income steps predate the current `debt_repayment` classification. Use `spec.md` and the debt activity design spec for current behavior.

> **For implementers:** Follow repository instructions and the execution method agreed with the user. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Capture debts without changing account balances by default; link explicitly requested advances and completed repayments in either direction; show each person's linked activity on the Debts page.

**Architecture:** Add a nullable `transactions.debt_id` foreign key and keep debt/ledger writes inside owner-scoped store transactions. The assistant's `log_debt` tool carries an explicit `recordTransaction` choice, defaulting to debt-only; explicit `owed_to_you` advances are expenses, explicit `you_owe` borrowings are income, and repayments link by direction. The debt read path returns linked activity for person grouping in the existing Debts view.

**Tech Stack:** Next.js 16.4 Route Handlers, TypeScript, better-sqlite3, React 19, Vitest.

**Spec:** `docs/specs/2026-10-13-14-07-debt-activity-by-person-design.md`

## Global Constraints

- Follow the root `AGENTS.md` debt repayment rules: one owner-scoped atomic `recordDebtPayment`; validate debt, amount, account, and income category before persistence; retain the last positive settled amount; do not add generic repayment Undo.
- Keep counterparty names out of the provider system prompt. Send only JSON-escaped counterparty and formatted amount as untrusted repayment context, and retain exact payer matching, no-write ambiguity handling, and overpayment rejection.
- Keep all new debt links owner-scoped. Do not guess links for existing transactions or manual debts.
- Keep `transactions.debt_id` nullable with `ON DELETE SET NULL`; leave existing records unlinked.
- Debt-only is the default for both directions. A clear user request is required to record the related transaction; missing account/category does not change that choice.
- Incoming repayment uses the existing `recordDebtPayment` income operation for `owed_to_you`. A payment the user makes against `you_owe` uses a separate atomic expense operation. An unmatched completed outgoing payment remains an ordinary expense.
- Preserve the current uncommitted feature changes in `src/lib/assistant.ts`, `src/lib/provider.ts`, `src/lib/store.ts`, and their tests. Do not stage or alter the existing `package-lock.json` change.
- Use existing Next.js 16.4 Route Handler conventions and existing UI styles; do not add dependencies.

## Review Focus

- Upgrading an existing database must leave old transactions with `debt_id = NULL`, and deleting a debt must preserve its ledger transactions.
- A linked transaction must not be deleted or change amount/kind while its debt exists; changing debt direction must also fail. Other allowed transaction edits must still preserve ledger totals.
- The explicit debt-only request must skip account/category lookup, while omitted opt-out defaults to an expense and missing setup still writes neither record.
- Repayments must match the named payer and exact open debt, reject overpayment, and roll back both writes on invalid account/category or ledger-total failure.
- Person grouping must be case-insensitive and direction-scoped, keep separate obligations, show chronological categorized movements, retain settled balances, and refresh after assistant activity.
