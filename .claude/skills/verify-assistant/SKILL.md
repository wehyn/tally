# Verify the assistant

**Property, in one sentence:** the assistant saves a transaction only when the user meant it, once, with consent, and an Undo only works inside its ten seconds and never on a debt repayment.
**Harm if broken:** money records the user did not ask for, duplicated, or recorded after they turned the assistant off.

Model: `model/Assistant.tla`, one conversation. A hand model proves nothing about the code by itself, so `model/conformance.test.ts` replays each fact the model assumes against the real store, route and `runAssistantPrompt`.

## Run it

1. Real-code replay (needs `npm ci` once): `.claude/skills/verify-assistant/model/check.sh`. All 16 tests must pass.
2. Model check. Use `/statechart` on `model/Assistant.tla` once per config, or run TLC directly with a `tla2tools.jar` (for example `java -cp tla2tools.jar tlc2.TLC -workers 4 -config model/core.cfg model/Assistant.tla` from `.claude/skills/verify-assistant`).
   - `model/core.cfg`: **must hold** (20,412 distinct states, a few seconds). A violation is a real break of a rule the code upholds at the sync commit.
   - `model/findings.cfg`: sets `Legacy = TRUE`, which replays the rules before the fixes. It **must fail** on the four invariants (`NoDuplicateIntentWrite`, `WriteNeedsConsent`, `FollowupSurvivesError`, `PlainPromptNotTrapped`). TLC reports the first one it reaches; to check a single invariant, put only that name on the `INVARIANTS` line.
   - `model/doubt.cfg`: sets `Doubt = TRUE`, which replays the replacement rule at `232f564` (kept until `b35b71b`), where any word beyond an amount, its peso marker and answer filler replaced a pending question, so "maybe 500" and "500 cash" dropped it. It **must fail** on `AnswerNotReplaced`.
   - `model/flows/*.cfg` with `model/views/*.mjs` redraw the charts in `docs/state-machines/assistant.md`. The renderer is not installed everywhere, so check the doc's charts by hand against the model when it is not.

## Fixed findings (kept as regression replays)

Each finding is fixed and pinned by a replay in `model/conformance.test.ts` (describe block "regressions") and a route test in `tests/assistant-route.test.ts` ("assistant turn commit").

1. **Duplicate save** (`c6f5d5b`). The write and its reply used to commit separately. Now `commitTurn` runs them in one store transaction. A deleted chat makes the reply insert throw, which rolls the write back. Replayed by `NoDuplicateIntentWrite (fixed)`.
2. **Save after consent withdrawn** (`d05bb50`). Access is checked again inside the commit transaction, before any write. The check lives in `commitTurn` itself, which every stored turn uses, so the local debt-list answer (no model call) is covered too; `tests/assistant-route.test.ts` pins that path ("refuses a local debt-list turn when consent is withdrawn while the request body streams"). Replayed by `WriteNeedsConsent (fixed)`.
3. **Failed model call drops the question** (`3f73ccd`). The user message is stored with the turn's commit, not before the call. A failed call stores nothing, so the pending question stays last. Replayed by `FollowupSurvivesError (fixed)`. The message is stamped with the time the request was received (`receivedAt`, taken at the start of `runAssistantPrompt` and passed through `commitTurn` to `addMessage`), not the commit time, because a later follow-up reads relative dates ("today") from it. "lunch today" sent at 23:59:59 and answered "250" after midnight still saves on the first day. `addMessage` stores that time as `created_at` as sent, with no clamp. An earlier version clamped it to never precede the latest message of the conversation, which overwrote the received time when the clock moved back two seconds across Manila midnight, so "lunch today" then "250" saved on the next day (S5, fixed in `497bff8`). `getConversation` lists a conversation by insertion order (rowid), which is prompt then reply because a turn commits both in one transaction, so a clock that moves backwards cannot reorder them. Pinned by route tests in `tests/assistant-route.test.ts` ("keeps today relative to when the request arrived ...") and `tests/store.test.ts`; the model has no dates, so there is no invariant.
4. **Unrelated prompt is swallowed** (`25e864f` for a pending repayment amount or ordinary income question, `64efa45` for a pending repayment payer question, redesigned in `497bff8`, `69d93e8` and `7f0e42f`). `pendingOutcome` in `src/lib/machines/assistant.ts` decides, from the facts `promptFacts` in `src/lib/assistant.ts` builds. The rule is closed-world. A reply to a pending question **replaces** it only on a positive signal. The prompt, once its amount is set aside, names one of the user's own category names or a word the category keyword map knows (`namesCategory`, `CATEGORY_KEYWORD_RULES`: coffee, lunch, grab, rent). An account name never counts, nor does the catch-all "Other". The prompt also carries a number, has no hedge or negation, is not payment wording, is not a yes or no, and names nobody with an open debt. "Coffee 120" replaces the question and runs with no prior context. **Every other reply is an answer.** The pending context is kept and the existing handling runs, so a reply it cannot read asks again and writes nothing. A wrong replace drops the pending context and the guards that read it, and can write money to the wrong place. A wrong answer only asks again. The replacement is persisted. The replacing user message is stored with `context_start = 1` and `minimalFollowUpContext` never reads past it, so the next turn of the new request ("Wallet" after "Which account?") cannot reload the abandoned question.

   **The broadened amount reading was removed.** An earlier version read an answer to the repayment amount question as an amount after stripping dates, account names, filler, and `k`, `m` and "thousand" shorthand, and let a named account override the model's. The amount is read as strictly as on main again. It is digits with an optional peso sign or word and nothing else ("500", "1,000.50", "₱500", "500 pesos"). So "500 cash", "5k", "500 sa GCash", "about 500" and "P500" after a repayment amount question re-ask for the amount and write nothing. They are not recorded as repayments. This is the deliberate safe default. A reply with a detail or a hedge costs the user one more message, and none of them can record a wrong amount, date or account.

   **History of findings.** The first replacement rule (`232f564`, kept through `2594b66`) replaced on any word beyond amount filler, so "maybe 500" saved a 500 expense and "500 cash" offered ordinary income while Ana's debt stayed (replayed by `doubt.cfg`). `b35b71b` added a hedge fact and word lists for dates, owned accounts and filler, and the amount reading was widened to match. Review round 3 then found six bugs in that one family. **O1**, the allow-list leak. Deciding by the absence of known filler let any unlisted wording count as a new subject ("She paid 500", "500 to Savings", "5 hundred", "500 ata", "mga 500"), so the pending repayment was dropped and an expense saved. **O2**. "about 500" was read as an exact 500 and recorded. **S1**. More hedge wording than the hedge list knew. **S2**. "in cash" was not recognized as a detail. **S3**. "from Savings to GCash" named two accounts and the reading had to pick one. **S4**. "last night" was stripped as a date, so the repayment recorded on today. **S5**. The clamp in finding 3. The premise changed because every fix extended a list of wording that can surround an amount, and each wording the lists missed was a wrong replace or a wrong exact amount. The new rule lists only what the app owns, the user's categories and the keyword map, so an unknown wording can only fall to answer. `497bff8`, `69d93e8` and `7f0e42f` deleted the filler, detail, date, account and extra hedge lists, the subject test, the broadened amount reading and the reply-account override. Replayed by `PlainPromptNotTrapped (fixed)`, `PlainPromptNotTrapped (payer)`, `PlainPromptNotTrapped (amount forms)`, `PlainPromptNotTrapped (stays replaced)`, `AnswerNotReplaced (hedged)` and `AnswerNotReplaced (detail)`. The wording tables are in `tests/assistant-machine.test.ts` and the flows in `tests/assistant-route.test.ts`.

## Telling a real bug from a modeling error

A `core.cfg` counterexample is a sequence of the model's actions (`YouSend`, `ProviderOk`, `YouUndo`, ...). Replay it in `tests/assistant-route.test.ts` style: one provider stub per `ProviderOk`, one `POST` per `YouSend`. If the real code does not reproduce it, the model is wrong: fix the model, never weaken the invariant. If it reproduces, report it with the steps in plain words; do not change product code unless asked.

## Updating after an intended change

New follow-up kind or branch: add it to `Kinds` and `Decision` with the new file:line, add an intent if a new prompt shape reaches it, add a conformance test that drives it, then rerun both checks.

Prove the check can still fail. `findings.cfg` does this for the four rules (`Legacy = TRUE`) and `doubt.cfg` for `AnswerNotReplaced` (`Doubt = TRUE`). For a single rule, copy the model to a scratch directory and weaken one guard. For example `CommitOk == conv = "live"` drops the consent re-check, and `WriteNeedsConsent` must fail. Or make `ProviderFail` clear `pend`, and `FollowupSurvivesError` must fail. Then confirm `core.cfg` holds again on the real model.
