# Verify the assistant

**Property, in one sentence:** the assistant saves a transaction only when the user meant it, once, with consent, and an Undo only works inside its ten seconds and never on a debt repayment.
**Harm if broken:** money records the user did not ask for, duplicated, or recorded after they turned the assistant off.

Model: `model/Assistant.tla`, one conversation. A hand model proves nothing about the code by itself, so `model/conformance.test.ts` replays each fact the model assumes against the real store, route and `runAssistantPrompt`.

## Run it

1. Real-code replay (needs `npm ci` once): `.claude/skills/verify-assistant/model/check.sh`. All 26 tests must pass.
2. Model check. Use `/statechart` on `model/Assistant.tla` once per config, or run TLC directly with a `tla2tools.jar` (for example `java -cp tla2tools.jar tlc2.TLC -workers 4 -config model/core.cfg model/Assistant.tla` from `.claude/skills/verify-assistant`).
   - `model/core.cfg`: **must hold** (55,593 distinct states, a few seconds). A violation is a real break of a rule the code upholds at the sync commit. `PlainPromptNotTrapped` says an explicit cancel always clears a pending question. An unrelated prompt asking the question again is a deliberate limit, so it is not an invariant. `AnswerNotReplaced` says only a cancel drops the question, and that a read-only turn (the debt list, a finance answer) leaves a pending question pending. A finance question at a pending income question is answered like any other and leaves that question pending too (`ordinaryIncomeTurn` returns `read`). `NonAnswerNeverWrites` says a reply that is not the answer to a pending repayment or income question writes nothing. `OneWritePerQuestion` says a pending question is answered with a write at most once, and `CancelledNeverAnswered` says a question a cancel dropped is never answered afterwards, even by an answer already in flight. Both depend on `Rival`, a second request that commits while ours waits on the model, and on `Fresh`, the commit check. `OpenRunBounded` says an open run is never extended past `RunMax` turns, because a turn that finds it there ends the question. `ExpiryWritesNothing` says that turn writes nothing. `AnswerNotReplaced` allows that end, and a cancel is not affected by it.
   - `model/findings.cfg`: sets `Legacy = TRUE`, which replays the rules before the fixes. It **must fail** on the four invariants (`NoDuplicateIntentWrite`, `WriteNeedsConsent`, `FollowupSurvivesError`, `PlainPromptNotTrapped`, which fails because before the fix a cancel left the question pending). TLC reports the first one it reaches; to check a single invariant, put only that name on the `INVARIANTS` line.
   - `model/race.cfg`: sets `Unchecked = TRUE`, which replays the code before the commit check (`326d565`). It **must fail** on `OneWritePerQuestion` and on `CancelledNeverAnswered`. TLC reports the first it reaches, so check each singly by putting only its name on the `INVARIANTS` line.
   - `model/unbounded.cfg`: sets `Unbounded = TRUE`, which lets a run that is at its limit keep going, as the code did before the limit (the cap at `4857caa` kept a trimmed run going too). It **must fail** on `OpenRunBounded` and on `ExpiryWritesNothing`. TLC reports the first it reaches, so check each singly by putting only its name on the `INVARIANTS` line.
   - `model/doubt.cfg`: sets `Doubt = TRUE`, which replays the older replace-on-text rule (`232f564`, then `7f0e42f`), where a hedged reply, an amount with a detail or a complete request replaced a pending question, so "maybe 500", "500 cash" and "Coffee 120" dropped it. It **must fail** on `AnswerNotReplaced` (and on `NonAnswerNeverWrites`, which you can check by putting that name alone on the `INVARIANTS` line).
   - `model/flows/*.cfg` with `model/views/*.mjs` redraw the charts in `docs/state-machines/assistant.md`. Without the `/statechart` command, dump the state graph with `-dump dot,actionlabels`, turn it into Mermaid with the view functions, and render it with Pele (flow 2 was built this way). ## Fixed findings (kept as regression replays)

Each finding is fixed and pinned by a replay in `model/conformance.test.ts` (describe block "regressions") and a route test in `tests/assistant-route.test.ts` ("assistant turn commit").

1. **Duplicate save** (`c6f5d5b`). The write and its reply used to commit separately. Now `commitTurn` runs them in one store transaction. A deleted chat makes the reply insert throw, which rolls the write back. Replayed by `NoDuplicateIntentWrite (fixed)`.
2. **Save after consent withdrawn** (`d05bb50`). Access is checked again inside the commit transaction, before any write. The check lives in `commitTurn` itself, which every stored turn uses, so the local debt-list answer (no model call) is covered too; `tests/assistant-route.test.ts` pins that path ("refuses a local debt-list turn when consent is withdrawn while the request body streams"). Replayed by `WriteNeedsConsent (fixed)`.
3. **Failed model call drops the question** (`3f73ccd`). The user message is stored with the turn's commit, not before the call. A failed call stores nothing, so the pending question stays last. Replayed by `FollowupSurvivesError (fixed)`. The message is stamped with the time the request was received (`receivedAt`, taken at the start of `runAssistantPrompt` and passed through `commitTurn` to `addMessage`), not the commit time, because a later follow-up reads relative dates ("today") from it. "lunch today" sent at 23:59:59 and answered "250" after midnight still saves on the first day. `addMessage` stores that time as `created_at` as sent, with no clamp. An earlier version clamped it to never precede the latest message of the conversation, which overwrote the received time when the clock moved back two seconds across Manila midnight, so "lunch today" then "250" saved on the next day (S5, fixed in `497bff8`). `getConversation` lists a conversation by insertion order (rowid), which is prompt then reply because a turn commits both in one transaction, so a clock that moves backwards cannot reorder them. Pinned by route tests in `tests/assistant-route.test.ts` ("keeps today relative to when the request arrived ...") and `tests/store.test.ts`; the model has no dates, so there is no invariant.
4. **Unrelated prompt is swallowed** (`25e864f` for a pending repayment amount or ordinary income question, `64efa45` for a pending repayment payer question, replaced by an explicit cancel in `481a0ff` and `39e0033`). "Coffee 120" after "What amount should I use for the repayment?" used to get the same question. The first fix let a prompt that looked like a new request replace the question, and four review rounds kept finding wording that the classifier read wrongly. **Now an explicit cancel is the only text that drops a pending question on purpose.** What else ends one is an answer that resolves it, a completed write and a run that grew too long (finding 8), and a hedged repayment reply ends it through the uncertainty guard, which asks first and writes nothing. `pendingOutcome` in `src/lib/machines/assistant.ts` returns "cancel" when the whole prompt, trimmed, case-folded and stripped of punctuation, equals one of `cancel`, `never mind`, `nevermind`, `skip`, `forget it`, `stop`, `ayoko na`, `wag na`, `huwag na`, `di na`, for any pending kind, and "answer" for everything else, including "no". A cancel calls no model, writes nothing and stores a reply with no pending kind, so a later turn never reloads the dropped question. Its reply is "Okay, I dropped that question. Nothing was recorded." unless the open run already saved a debt (the offer to add a just-saved debt to Transactions and the questions that continue it), where it says "The debt stays in Debts, and nothing was added to Transactions.", or a bill, where it says "The bill stays in Bills, and nothing else was recorded.", or both (`cancelReply` and `runSaved` in `src/lib/machines/assistant.ts`). With nothing pending, a cancel phrase is an ordinary prompt. **Every other reply is an answer.** The pending context is kept and the handling from main runs, so a reply it cannot read asks again and writes nothing. An unrelated prompt such as "Coffee 120" is therefore asked about again until the user says cancel. That is a deliberate limit, accepted because a wrong replace drops the context and the guards that read it and can save an expense while the debt stays open, and a wrong answer only costs a message. To make the way out visible, a re-ask ends with `cancelHint` ("Reply with the amount, or say cancel to drop this." for the amount question, "Reply with the person's name, or say cancel to drop this." for the payer question, "Or say cancel to drop this." for the income, account or date and bill questions). A first ask, a question the model worded itself (`modelWorded` in `runAssistantPrompt`, true when the turn's call is the provider's own `ask_clarification`, even when it is stored as `repayment_amount`) and the offer to add a debt to Transactions carry no hint.

   **Why text-based replacement was abandoned.** Rounds 2 and 3 leaked through allow-lists of filler, hedge, date and account words, so "maybe 500", "500 cash", "She paid 500", "500 to Savings", "5 hundred" and "mga 500" replaced the question. The round 3 redesign, a positive category-evidence rule, leaked in round 4 through category words inside real answers and payment statements ("she paid back the food money, 500", "bayad sa food 500"), hedge words next to a category ("I guess Food 500", "siguro Food 500") and an account named like a category ("to Food Wallet 500"). Each of these dropped the pending repayment, saved an expense with a ten second Undo and left the debt open. The broadened amount reading from the same family was removed earlier: the amount is read as strictly as on main again, digits with an optional peso sign or word and nothing else, so "500 cash", "5k", "500 sa GCash", "about 500" and "P500" re-ask and write nothing.

   Replayed by `PlainPromptNotTrapped (fixed)`, `PlainPromptNotTrapped (stays cancelled)`, `PlainPromptNotTrapped (payer)`, `PlainPromptNotTrapped (amount forms)`, `NoPendingNoCancel`, `AnswerNotReplaced (hedged)`, `AnswerNotReplaced (detail)` and `AnswerNotReplaced (category word)`. The reply wording tables are in `tests/assistant-machine.test.ts` and the flows in `tests/assistant-route.test.ts`.

5. **Two requests on one question** (`e34c223`). A turn read the pending question before the model call and stored its user message only at commit, and the commit never checked that the question was still the one it read. The same answer sent twice while the first waited on the model wrote two repayments, and an answer in flight committed after a cancel had dropped its question and wrote a repayment anyway. `commitTurn` now compares the conversation's last stored message with the one the turn read, inside the commit transaction (`turnMayCommit`, `store.lastMessageId`), and refuses a stale turn with 409 "Your conversation changed while this ran. Send that again." without storing anything. It holds for every stored turn, and for a new chat, which must still have no message. Replayed by `OneWritePerQuestion (fixed)` and `CancelledNeverAnswered (fixed)`, which drive two requests through the route with a model call held open. A request that is refused this way is not retried by the server. The user sends it again, and it then reads the current conversation.

6. **A question lost without a cancel** (`de28309`, `4857caa`). "Ana paid me" asked for an amount, and then "List my debts", a plain finance question or a bill saved without a question stored its reply with no pending kind, so the following "500" reached the model with no repayment context and a model `log_transaction` saved a 500 expense while the debt stayed open. A finance question with a question mark was also replaced by the uncertainty guard's "I didn't record anything". Separately, six re-asks pushed the original payer statement out of the 12-message cap, which the first fix answered by keeping the run's first message. `followupAfterTurn` now stores a read-only reply, or the reply to a bill saved without a question while a question that is not about a bill was pending, with the pending kind and the offered debt carried forward. The uncertainty guard no longer replaces a finance answer while a question is pending, and the cap that kept the first message of an open run and trimmed the middle was replaced in round 7 (finding 8). Replayed by `AnswerNotReplaced (read-only)` (two replays) and `PlainPromptNotTrapped (long run)`. The model has the read-only turn as the `readOnly` intent. One limit stays. A bill request that asks its own question takes over the pending slot. The text of a quiet turn no longer reaches the local reading of the run (finding 10).

7. **A saved bill left its own question pending** (`32508d9`, review round 7). A bill question such as `bill_amount` stayed pending after "549" saved the bill, so the next expense was forced into the bill flow and "cancel" said nothing was recorded although the bill existed. `followupAfterTurn` now ends a pending bill question when a bill is saved or updated without a question, because that save answers it, and still leaves a question that is not about a bill pending. Pinned by the machine table in `tests/assistant-machine.test.ts` and route tests in `tests/assistant-route.test.ts`, not by the model, which has no bill kinds.

8. **A trimmed run lost what the question was about** (`655593b`, review round 7). The cap kept the first message of a long run and the 11 most recent, but a run can hold two questions and corrections inside it were trimmed. A sixth "Coffee 120" re-ask after "Coffee", then "Actually, Ana paid me", dropped the repayment question and saved an expense, and "Use Wallet" after "Actually Bob paid me 500", "Bob" and six debt lists repaid Ana. The trimming is gone, because choosing which messages to keep is itself a guess. The whole open run reaches the model, and `runExpired` bounds it: a turn that is not an exact cancel and finds the run at `MAX_OPEN_RUN_MESSAGES` (24) calls no model, writes nothing and stores `expiredReply` with no pending kind, so the question ends and the next prompt runs clean. It counts re-asks, read-only turns and answers alike, and an exact cancel at the limit still gets the cancel reply. Replayed by `OpenRunBounded (fixed)` (two replays) and `ExpiryWritesNothing (fixed)`. The model counts turns (`runLen`, `RunMax`) and has `OpenRunBounded` and `ExpiryWritesNothing`. The cost is that a question left open through 12 exchanges has to be asked again, a limit we accepted. A run just under the limit that names two payers asks which person and writes nothing, which is the safe direction.

9. **A cancel or an expiry said nothing was recorded after a bill was saved** (`e066d5a`, review round 8). A bill saved under a pending repayment question leaves the question pending, and the bill may have posted its due-today expense, but the reply came from the saved debt alone. A reply now stores the bill it saved (`bill_id` on the assistant message), `runSaved` reports the debt and the bill of the open run, and `cancelReply` and `expiredReply` say "The bill stays in Bills, and nothing else was recorded." for a bill and name both for a debt and a bill. Bill questions are not modeled, so there is no invariant. Pinned by the machine tables and three route tests in "assistant turn commit".

10. **A quiet turn moved a repayment's account and date, and then hid its own refusal** (`0314611` and `a3c3c66`, review rounds 9 and 10). A bill saved without a question, or a read-only answer, leaves the pending question pending, but its user message stayed in the open run and the account and date hints were read over the whole run, so a Netflix bill using Savings that starts tomorrow sent "Ana paid me 500" to Savings on the next day, and a finance question that carried a date replaced the repayment date. `isQuietReply` marks a reply that kept the question and either carries the bill it saved (`bill_id`) or has `read_only` set on the assistant message, and `ownUserMessages` keeps the user messages of the run that belong to the question. The first fix read all user text from those, which hid a refusal said in a quiet turn from the write guards, so "Actually, Ana did not pay me. List my debts." and then "500" recorded the repayment. `userMessagesFor` now splits the reads. A hint reads only the messages that belong to the question and the current prompt (the account, date, time, category and opt-in read only the current statement of them, finding 18; the amount, the payer, the debt named and the bill details read all of them; the yes for ordinary income is the current message alone). A guard that can only refuse or ask (`uncertainRepayment`, the uncertain new debt check, the opt-out from Transactions, the payment wording that stops an income confirmation) reads every user message of the run and the current prompt. The model still sees the whole run. A correction inside the run ("Actually into Savings") is not quiet and still takes effect. Not modeled, since the model has no messages, so there is no invariant. Pinned by the machine table, a store test for the column and the route tests in "quiet turns inside a pending repayment run".

11. **A guard replied "nothing was recorded" after the turn had written** (`124949b`, review round 11). `a3c3c66` read refusal wording over the whole run but applied the guard at the end of the turn and replaced the reply, so "yes" to the ordinary income question after "Actually, Zed did not pay me. List my debts." saved the income and then said "I didn't record anything", and a valid due-today bill after the same quiet negation saved the bill and its expense under the same denial. The decision is now taken before any branch can write: `turnCallOf` classifies the final call and `refusalOutcome` returns `proceed`, `askAgain` (a refusal in an earlier turn and a call that would write: write nothing, keep the question pending, say so), `refuse` or `endQuestion` (a refusal in the current message), and `endedQuestionReply` says nothing was recorded only for a turn that wrote nothing. Not modeled, since the model has no messages, so there is no invariant. Pinned by the machine table and by the route test "a denying reply never coexists with a committed write", which compares ledger rows before and after each branch.

12. **A "no" prefix declined income the user had confirmed** (`ecad4c6`, review round 12). `ordinaryIncomeDeclined` matched any reply that began with "no", so "No, use Wallet. I still want to record it as income." after a held "yes, into my Nowhere account" saved nothing and dropped the question. Pinned by the machine table "the ordinary income decline" and the route tests named in the doc.

13. **An earlier held yes outlived a refusal that was not an exact decline** (`28a15c8`, review round 13; `ecad4c6` left it). "Zed paid me 500", "yes, into my Nowhere account", then "No, don't record it", "No, never mind" or "no, I changed my mind" saved the income to Wallet, because `ordinaryIncomeAccepted` stayed true after any earlier yes. `28a15c8` vetoed a held yes when the reply led with no, nope, nah, hindi or ayoko (`vetoesHeldIncomeYes`), a second word list that finding 14 shows leaking in both directions and removes. Not modeled, since the model has no messages, so there is no invariant.

14. **A held yes must not authorize a later write** (`55ed64e`, review round 14). After "Zed paid me 500" and a yes held for an account, a refusal that did not lead with no still wrote and answered "Saved": "Don't record it", "I changed my mind, don't record it", "Wallet, but don't record it", "Actually, skip recording it as income", "Not as income", "Hold on, don't record that". The leading-no veto also turned "No expenses this month? Show my spending totals." into an income re-ask that replaced the account clarification and lost the held confirmation, so a following reply failed to save. **No earlier message authorizes a write now. The ordinary income write needs the message being answered to be a yes itself** (`isIncomeConfirmation`: yes, yeah, yep, sure, okay, ok, go ahead, record it, record that, in leading position), decided by the pure function `ordinaryIncomeTurn(prompt, call)` in `src/lib/machines/assistant.ts`: `decline` for an exact decline phrase, `write` for a confirmation, `read` for a read-only call (answered by the ordinary read-only rules, the question stays pending as it was) and `askAgain` for everything else (nothing written, the income question again with the cancel hint, stored as ordinary_income). When a yes needs an account or date, the reply says how to confirm: "Reply with yes and the account, like \"yes, Wallet\", or say cancel." (`incomeConfirmHint`). The flow stays open for the run once the question was asked (`ordinaryIncomeOpen`). `vetoesHeldIncomeYes`, `incomeConfirmed`, `ordinaryIncomeConfirmedInHistory` and the `heldYesVetoed` flag are gone. Accepted costs: a bare "Wallet" after the account question asks once more, and "Okay, don't record it" starts with a yes word and is still read as a yes, the same as a plain yes. Not modeled; the model's `yes` and `readOnly` intents already match. Pinned by the table "the ordinary income turn" in `tests/assistant-machine.test.ts` and the route tests that name the six refusals and the finance question, and by the refusals in "a denying reply never coexists with a committed write".

15. **"yes, <name>" named an account for every caller** (`9c496dc`, review round 15). `55ed64e` made `accountMention` read "yes, Wallet", so a payer pick "yes, Maya" (Ana and Maya paid me 500 into Wallet; Maya is also an account) sent the money to the Maya account instead of the named Wallet, and the debt-to-Transactions yes leaked the same way. `accountMention` is cue words only again; the cue-free parse is `incomeConfirmationAccount`, used only by the income write (`ordinaryIncomeTurn` returned `write`). Not modeled. Pinned by "the account an income write may use" in `tests/assistant-machine.test.ts` and "assistant account named by a yes reply" in `tests/assistant-route.test.ts`.

18. **A hint leaked from an earlier, different payment of the same run** (`9d825dc`, review round 18; what starts a statement replaced in `705b57f`, the text rule's errors made harmless in `1c47b27`). The account, date, time and category hints were read over every non-quiet user message of the open run, so "Zed paid me 500 into Maya on 2026-10-01", "Actually Ben paid me 200" and "yes" wrote Ben's 200 into Maya on Oct 1, a later "Ben paid me 200" with an open debt wrote a repayment there (no Undo), and the same leaked through outgoing repayments, debt advances (and an earlier opt-in to Transactions) and bills with their posted expense. "Last Monday" in the earlier payment made a later write take or ask for a date. **The rule: a hint applies only to the statement the write is for.** `hintMessagesFor` is the one pure function that says which user messages that is: from the latest message that started a different statement to the end of the run, quiet turns left out, empty when the current message starts its own. Every write path feeds its account, date, time, category and opt-in hints from it, while the payer, the amount, the bill details and every guard keep reading the whole run. What starts a statement was replaced in finding 19: the kind the reply before it stored decides, and only an explicit restart starts one, so a correction in the same statement still applies. Not modeled. Pinned by "the user messages a hint may read" in `tests/assistant-machine.test.ts` and "a hint applies to the statement it was said for" in `tests/assistant-route.test.ts`.

19. **The text recognizer for a new statement misfired both ways** (`705b57f`, review round 19). `9d825dc` decided by text whether a reply opens a statement, so a numeric answer ("Actually 200" to the income question, "use BPI 2" or "use BPI 1234" to an account question, "Add it to Transactions for the 500 lunch" to the debt opt-in), a payment-worded bill answer ("I paid 549") and a date or time answer lost the earlier account, date or time and wrote Wallet or today silently, while "Instead, log salary 5000" under a clarification was taken for an answer and kept Maya and Oct 5. **The rule: the stored kind of the pending question decides, and the text rule is narrow.** `startsNewStatement` (pure, a table over every followup kind): a reply starts a new statement only with no question pending, or when it states an amount (no date, no time, no account name) with a purpose or counterparty word and either carries restart wording (a leading instead, actually, never mind, scratch that, forget that, ignore that, or a trailing instead) or comes under a clarification, an account or date question, the income question or the repayment amount question with a word the statement did not already name. A reply that starts with use, choose, select, switch, change, set, make it or put it answers. Anything else is an answer and keeps the cue. Not modeled. Pinned by "whether a reply starts a new statement" and "the user messages a hint may read" in `tests/assistant-machine.test.ts` and "a reply to a pending question keeps its statement's hints" in `tests/assistant-route.test.ts`.

20. **A classifier error silently moved the money** (`1c47b27`, review round 20). Six more replies the text rule misread, all silent: a payer named like an account ("Maya paid me 200" after "Log coffee into BPI on 2026-10-05 at 8pm" wrote a repayment with no Undo into BPI on Oct 5 at 20:00), "Make it salary 5000 instead" (a command lead returns before restart wording is read, so the earlier expense's account and time stayed), "Actually coffee 120" (the same transaction read as a restart lost its account, date and time), "120 at 1130pm" (a compact time left "pm" as a purpose word), a bill detail answer with restart wording and an extra word ("Actually it is 549 monthly", "Actually 12 payments") that saved the bill and its expense in the default account, and a date, time or amount answer with a leftover digit and a word ("12 noon", "3 in the afternoon", "500 po", "500 bucks"). **The rule: a hint classification is never trusted when it would change the write.** The word lists were not patched. `readStatementStart` (pure) returns the verdict and whether the reply is shaped like a restart the rule cannot be trusted to read (it states an amount and a purpose or counterparty word, an account name kept in place and no command exemption, and carries restart wording or comes under a kind that allows a restart without wording with a word the statement did not name). `hintReadingsFor` returns the rule's own reading of the run and, when turning the unsure verdicts over gives other messages, the other reading. Every write path computes its account, date and time under both readings (`writePlaceOf` in `assistant.ts`): income, received and paid repayments, a debt with its transaction, and a bill with its posted expense. If `ambiguousHints` says they differ, nothing is written: the turn asks "Do you mean the earlier <description> in <account> on <date>, or a new one? Reply with the account and date, or say cancel." (`account_or_date`, `bill_account` for a bill) and the reply writes only when it names the account and the date on which the readings differ (`ambiguityVerdict`); any other reply asks again. A pure answer by its kind or shape ("use BPI 2", "Coffee 120", "Actually 200") is never unsure, and a restart whose two readings agree writes. Accepted costs: a restart with a different payer or purpose that says no account or date now asks once when the statement before it did, a bill answer loses its amount across the question (the reply states it again), and the answer to the question writes the code's own reading, so its time follows that reading. Not modeled. Pinned by "when the text rule is unsure whether a reply starts a new statement" and "where a write would put the money under two readings" in `tests/assistant-machine.test.ts` and "a reply the text rule is unsure about never writes a place the reading would change" in `tests/assistant-route.test.ts`.

A `core.cfg` counterexample is a sequence of the model's actions (`YouSend`, `ProviderOk`, `YouUndo`, ...). Replay it in `tests/assistant-route.test.ts` style: one provider stub per `ProviderOk`, one `POST` per `YouSend`. If the real code does not reproduce it, the model is wrong: fix the model, never weaken the invariant. If it reproduces, report it with the steps in plain words; do not change product code unless asked.

## Updating after an intended change

New follow-up kind or branch: add it to `Kinds` and `Decision` with the function that asks it, add an intent if a new prompt shape reaches it, add a conformance test that drives it, then rerun both checks.

Prove the check can still fail. `findings.cfg` does this for the four rules (`Legacy = TRUE`), `doubt.cfg` for `AnswerNotReplaced` (`Doubt = TRUE`), `race.cfg` for the two concurrency rules (`Unchecked = TRUE`) and `unbounded.cfg` for the two run limit rules (`Unbounded = TRUE`). The read-only part of `AnswerNotReplaced` has no config of its own. Copy the model to a scratch directory, change the `readOnly` case of `Decision` to `next |-> "none"`, and `AnswerNotReplaced` must fail on `core.cfg`. For a single rule, copy the model to a scratch directory and weaken one guard. For example `CommitOk == conv = "live"` drops the consent re-check, and `WriteNeedsConsent` must fail. Or make `ProviderFail` clear `pend`, and `FollowupSurvivesError` must fail. Then confirm `core.cfg` holds again on the real model.
